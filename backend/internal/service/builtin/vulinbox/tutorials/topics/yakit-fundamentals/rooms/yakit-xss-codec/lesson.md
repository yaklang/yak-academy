# XSS 与转义：用 Codec 看懂编码的边界

## 原理背景

**反射型 XSS** 的根因是：服务端把用户输入**原样拼接**进 HTML 响应。输入 `<script>alert(1)</script>`，返回的页面里就真的多出一段脚本——浏览器分不清"这是用户说的"还是"这是开发者写的"。

正确的防御是 **HTML 实体转义**：把 `<` 变成 `&lt;`、`>` 变成 `&gt;`，浏览器就只当它是不想被解释的普通文本。安全工程师的日常之一，就是对着响应原文确认"到底转没转义、转义成了什么"。

## Yakit 操作步骤

**Web Fuzzer 看响应原文**：

1. 进入 Web Fuzzer，构造 `GET /xss/echo?name=xxx` 请求（`Host` 只写 `主机:端口`，不带 `http://`）发送；
2. 在响应 body 里找到 `name` 参数出现的位置，确认它是否被转义。

**Codec 编解码对照**：

1. 打开工具集里的 **Codec 编码解码**；
2. 输入 `<script>`，选择 HTML 实体编码，观察输出；
3. 反向把一段实体文本解码回原文——编解码两个方向都要会，攻击时编码 payload、复盘时解码响应。

## 开始实战

点击 **前往配套题目练习**，启动环境后：请求 `/xss/echo` 确认输入被原样反射（这就是反射型 XSS），再请求安全版 `/xss/safe`，观察 `<script>` 被转义成 HTML 实体（`&lt;script&gt;`）——两种输出对照就是本课的知识点。观察完成后读取靶机 flag（`GET /flag`）并提交，完成本题。

**第 1 步：启动实验环境**

题目详情页点「启动实验环境」，等状态 running，复制访问地址（形如 `http://127.0.0.1:36870`）。

**第 2 步：请求危险版 /xss/echo，确认原样反射**

在 Web Fuzzer 发送（URL 里的特殊字符已编码，可整行照抄）：

```http
GET /xss/echo?name=%3Cscript%3Ealert(1)%3C/script%3E HTTP/1.1
Host: 127.0.0.1:36870
```

在响应 body 里搜索 `name` 的位置：你输入的 `<script>alert(1)</script>` **原样**出现在页面里——浏览器渲染时会把它当脚本执行，这就是反射型 XSS。（用浏览器直接访问该 URL 并关闭拦截也可能弹出弹窗，效果相同。）

**第 3 步：请求安全版 /xss/safe，读取转义后的原文**

```http
GET /xss/safe?name=%3Cscript%3E HTTP/1.1
Host: 127.0.0.1:36870
```

这次 `name` 的位置输出的是：

```
&lt;script&gt;
```

`<` 变成了 `&lt;`、`>` 变成了 `&gt;`——浏览器只把它当普通文本渲染，脚本永远不执行。

**第 4 步：用 Codec 验证你抄对了**

打开 Codec，把 `&lt;script&gt;` 做 HTML 实体**解码**，得到 `<script>`——与你第 3 步的输入一致，说明转义片段抄写无误。

**第 4 步：读取本实例 flag**

靶机为本次启动的环境单独生成了唯一 flag（形如 `flag{lab-xxxx}`），存在靶机文件系统的 `/flag.txt`，也可以直接请求靶机根路径的读取端点：

```http
GET /flag HTTP/1.1
Host: 127.0.0.1:36870
```

响应就是 flag 原文（一行，`flag{lab-...}`）。

**第 5 步：提交答案**

回到题目详情页，在答案框输入刚读到的 flag 原文（`flag{lab-...}` 整串）提交。
