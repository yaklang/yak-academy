# XSS 与转义：用 Codec 看懂编码的边界

## 原理背景

**反射型 XSS** 的根因是：服务端把用户输入**原样拼接**进 HTML 响应。输入 `<script>alert(1)</script>`，返回的页面里就真的多出一段脚本——浏览器分不清"这是用户说的"还是"这是开发者写的"。

正确的防御是 **HTML 实体转义**：把 `<` 变成 `&lt;`、`>` 变成 `&gt;`，浏览器就只当它是不想被解释的普通文本。安全工程师的日常之一，就是对着响应原文确认"到底转没转义、转义成了什么"。

## Yakit 操作步骤

**Web Fuzzer 看响应原文**：

1. 进入 Web Fuzzer，构造 `GET /xss/echo?name=xxx` 请求（Host 指向靶机）发送；
2. 在响应 body 里找到 `name` 参数出现的位置，确认它是否被转义。

**Codec 编解码对照**：

1. 打开工具集里的 **Codec 编码解码**；
2. 输入 `<script>`，选择 HTML 实体编码，观察输出；
3. 反向把一段实体文本解码回原文——编解码两个方向都要会，攻击时编码 payload、复盘时解码响应。

## 开始实战

点击 **前往配套题目练习**，启动环境后：

1. 在 Web Fuzzer 里请求 `/xss/echo?name=<script>alert(1)</script>`（或经浏览器直访），确认脚本能"注入"进页面——这就是反射型 XSS；
2. 再请求安全版 `/xss/safe?name=<script>`，观察 `<script>` 被转义后的输出**原文**；
3. 题目要求提交的正是这个转义结果：以 `&` 开头、`;` 结尾的完整片段。用 Codec 的 HTML 实体解码验证一遍你抄对了；
4. 思考：为什么 echo 版本 dangerous、safe 版本无害？差异只在一个转义函数。

## 延伸：自动化对照

Yakit 的**漏洞检测**（主动扫描）里包含 XSS 检测规则，对靶机跑一次扫描，观察它能否自动发现 `/xss/echo` 的问题——自动化找到漏洞边界，人工确认利用方式，这是实战的标准分工。Codec 还有 base64、URL、hex、哈希等几十种变换，后面教程会反复用到。
